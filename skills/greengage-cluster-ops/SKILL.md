# Operating a Greengage cluster

A Greengage cluster is one coordinator postmaster plus N segment postmasters plus optional
mirrors and a standby coordinator. Almost every operational surprise comes from one of
three places: you were talking to a different cluster than you thought, you read
`gp_segment_configuration` as if a mirror-role row were an error, or you ran a `gp*`
utility with half an environment.

## Step 0: the mode gate — decide this before typing anything else

Every other skill in this plugin defers to this gate. Run the detection first, then pick
exactly one mode.

```sh
# Detection, in this order. Stop at the first hit.
env | grep -E '^(PGPORT|PGHOST|PGDATABASE|COORDINATOR_DATA_DIRECTORY|MASTER_DATA_DIRECTORY)='
pg_isready -h "${PGHOST:-localhost}" -p "${PGPORT:-5432}"
ls gpAux/gpdemo/gpdemo-env.sh 2>/dev/null && cat gpAux/gpdemo/gpdemo-env.sh
```

| Mode | Choose when | First action |
|---|---|---|
| **attach** | `pg_isready` returns `accepting connections`, or `gpAux/gpdemo/gpdemo-env.sh` exists and its `PGPORT` answers | Source the environment (next section), then `gpstate -s` |
| **provision locally** | A source checkout with `$prefix/greengage_path.sh` present, nothing listening | `make create-demo-cluster` — see [reference/provisioning.md](reference/provisioning.md) |
| **provision in docker** | No local build, or you want isolation from an existing cluster | `docker build -f ci/Dockerfile.ubuntu` — see [reference/provisioning.md](reference/provisioning.md) |

**Never provision on top of a live cluster.** `make create-demo-cluster` runs
`demo_cluster.sh`, which starts with `rm -rf $DATADIRS` (`gpAux/gpdemo/demo_cluster.sh`,
the `if [ -d $DATADIRS ]` block before `mkdir $DATADIRS`). If a demo cluster is already
running on those ports the data directories go away under the running postmasters.
`create-demo-cluster` does **not** check ports first — `checkDemoConfig()` runs only under
`demo_cluster.sh -c` (`make -C gpAux/gpdemo check`), and it only looks for a
`/tmp/.s.PGSQL.<port>` file. Run it first, and treat `Port <n> appears to be in use.` as a
stop sign, not a prompt to raise `PORT_BASE` until something free is found.

## Environment first: sourcing one script is not enough

Two scripts, two disjoint jobs. Sourcing only one is the single most common silent
failure, because the shell keeps working and the utilities keep running — against the
wrong thing or not at all.

| Script | Exports | What breaks without it |
|---|---|---|
| `$prefix/greengage_path.sh` | `GPHOME`, `PATH`, `PYTHONPATH`, `LD_LIBRARY_PATH`, `OPENSSL_CONF` (generated by `gpMgmt/bin/generate-greengage-path.sh`) | `gpstate: command not found`; or, worse, a `gp*` from a *different* install is first on `PATH`. `gpconfig` exits with `Cannot import modules.  Please check that you have sourced greengage_path.sh.` |
| `gpAux/gpdemo/gpdemo-env.sh` | `PGPORT`, `COORDINATOR_DATA_DIRECTORY`, `MASTER_DATA_DIRECTORY` — nothing else | `GpError: Environment Variable COORDINATOR_DATA_DIRECTORY not set!` (`gpMgmt/bin/gppylib/commands/gp.py:1230`). On 6.x the string is `Environment Variable MASTER_DATA_DIRECTORY not set!` (`gp.py:1207`) |

`greengage_path.sh` sets **no** `PGPORT` and **no** data directory. That is the trap: with
only it sourced, `psql` silently falls back to port 5432 and `gpstate` aborts; with only
`gpdemo-env.sh` sourced, `psql` finds the right cluster but no `gp*` utility is on `PATH`.

```sh
source /usr/local/gpdb/greengage_path.sh          # 7.x README prefix
source gpAux/gpdemo/gpdemo-env.sh                 # from the source checkout root
```

Real prefixes seen in the wild: `/usr/local/gpdb` (7.x README source build),
`~/build/greengage-db-devel` (6.x `gpAux` build, `GPROOT` base),
`/usr/local/greengage-db-devel` (CI/docker `install_and_configure_gpdb`),
`/opt/greengagedb/greengage6/` (`.deb` package). `gpdemo-env.sh` is generated by
`demo_cluster.sh` and git-ignored (`gpAux/gpdemo/.gitignore`); if it is missing, the
cluster it described is gone — do not hand-write one.

**Non-demo cluster.** There is no `gpdemo-env.sh`. The equivalent is the installed
`greengage_path.sh` plus, exported by hand:

```sh
export COORDINATOR_DATA_DIRECTORY=/data/coordinator/gpseg-1   # 7.x
export MASTER_DATA_DIRECTORY=/data/master/gpseg-1             # 6.x
export PGPORT=5432
```

Verify you are pointed where you think before running anything destructive:

```sql
SELECT current_setting('data_directory'), current_setting('port'), version();
```

## Reading cluster health: `gp_segment_configuration` is the only source of truth

Shared catalog, identical column set on both lines: `dbid, content, role, preferred_role,
mode, status, port, hostname, address, datadir` (verified in
`src/include/catalog/gp_segment_configuration.h` on 7.x and
`src/include/catalog/gp_segment_config.h` on 6.x — the header was renamed, the columns
were not).

| Column | Values | Meaning |
|---|---|---|
| `dbid` | int16, unique | Physical instance id |
| `content` | int16, `-1` = coordinator/standby | Logical slice of the data |
| `role` | `p` / `m` | What this instance is doing **right now** |
| `preferred_role` | `p` / `m` | What it was created to do |
| `mode` | `s` in sync / `n` not in sync | WAL replication state of the pair |
| `status` | `u` up / `d` down | What FTS last observed |

The grouped health query — run this first, always:

```sql
SELECT status,
       role = preferred_role AS in_preferred_role,
       mode,
       count(*) AS segments
FROM   gp_segment_configuration
WHERE  content > -1
GROUP  BY 1, 2, 3
ORDER  BY 1, 2, 3;
```

Healthy is exactly one row: `status = 'u'`, `in_preferred_role = t`, `mode = 's'`.
Anything else is one of two distinct problems, and they need different fixes:

| Signature | Query | Meaning | Fix |
|---|---|---|---|
| `status = 'd'` | `WHERE status = 'd'` | FTS could not reach the instance, or it never started | `gprecoverseg` — see [reference/recovery.md](reference/recovery.md) |
| `role <> preferred_role` | `WHERE role <> preferred_role` | A failover already happened and succeeded. Nothing is broken; the layout is lopsided — two primaries now live on one host | `gprecoverseg -r`, and only after every pair is `mode = 's'` |

```sql
-- Down instances, with everything you need to go look at them
SELECT dbid, content, role, preferred_role, mode, status, hostname, port, datadir
FROM   gp_segment_configuration
WHERE  status = 'd'
ORDER  BY content, dbid;

-- Failed over but never rebalanced
SELECT content, role, preferred_role, status, hostname, port
FROM   gp_segment_configuration
WHERE  role <> preferred_role
ORDER  BY content;
```

**Trap: `mode = 'n'` on `content = -1` is normal, not a fault.** The coordinator row
always reads `n` and the standby row always reads `s`, and neither reflects real
replication state — the documented behaviour on
[gp_segment_configuration](https://greengagedb.org/en/docs-gg/current/reference/pg_catalog/gp_segment_configuration.html).
That is why the health query above filters `content > -1`. Judge the standby with
`gp_stat_replication`, below. On a mirrorless cluster every segment row also reads `n`;
that is normal too, because there is nothing to sync with.

**The audit trail.** `gp_configuration_history` (columns `time`, `dbid`, `description`;
shared catalog on both lines) records every FTS decision, with rows literally reading
`FTS: update role, status, and mode for dbid %d with contentid %d to %c, %c, and %c`
(`src/backend/fts/fts.c`). Use it to answer "when did this break", which
`gp_segment_configuration` cannot:

```sql
SELECT time, dbid, description
FROM   gp_configuration_history
ORDER  BY time DESC
LIMIT  50;
```

FTS re-probes on a timer, so the catalog lags reality by up to `gp_fts_probe_interval`
(default `60s`, `PGC_SIGHUP`, `src/backend/utils/misc/guc_gp.c`). After fixing something,
force a probe instead of waiting: `SELECT gp_request_fts_probe_scan();`

## `gpstate` is the same facts, plus what the catalog cannot see

`gpstate` connects to each instance, so it catches things the coordinator's catalog does
not — a missing `postmaster.pid`, a stale `/tmp` lock file, an instance the coordinator
believes is up.

| Flag | Shows | Use it when |
|---|---|---|
| *(none)* | Default summary | First look |
| `-s` | Full per-instance status | Diagnosing anything |
| `-e` | Only what needs attention | Scripted health checks — **exits 1** when anything is wrong |
| `-Q` | Counts from `gp_segment_configuration` only — prints `-Quick Greengage database status from Coordinator instance only` (6.x: `from Master instance only`) and never contacts a segment | The cluster is slow or partly unreachable |
| `-m` | Mirror list | Checking mirror placement |
| `-c` | Primary-to-mirror mapping | Before a rebalance |
| `-f` | Standby coordinator information (7.x help text: "standby coordinator"; 6.x: "standby master") | Standby health |
| `-b` | Status statistics | Summary counts |
| `-p` | Port information | Port conflicts, utility-mode connections |
| `-i` | Version of every instance | After an upgrade — mismatches cause `Catalog Versions are incompatible` at `gpstart` |
| `-x` | `gpexpand` status | During an expansion |

Flags read from `gpMgmt/bin/gppylib/programs/clsSystemState.py` (`gpstate` itself is a
16-line shim). Its section headings are exact strings worth grepping for:

- `All segments are running normally` — the only clean result
- `Segments with Primary and Mirror Roles Switched` — the `role <> preferred_role` case
- `Unsynchronized Segment Pairs` — `mode = 'n'`, rebalance is not yet safe
- `Downed Segments (may include segments where status could not be retrieved)`
- `Segments in recovery` — a `gprecoverseg` is in flight
- `DATABASE IS PROBABLY UNAVAILABLE`

## The standby is judged by replication, not by `status`

`gp_stat_replication` (defined in `src/backend/catalog/system_views.sql` on both lines) is
`pg_stat_replication` unioned across the coordinator and every mirror, with two extra
columns: `gp_segment_id` and `sync_error`.

```sql
-- 7.x (PostgreSQL 12 column names)
SELECT gp_segment_id, application_name, state, sync_state, sync_error,
       sent_lsn, flush_lsn, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_bytes_behind
FROM   gp_stat_replication
ORDER  BY gp_segment_id;
```

`gp_segment_id = -1` is the standby coordinator. `state = 'streaming'` and
`sync_state = 'sync'` is healthy.

**6.x delta:** PostgreSQL 9.4 column names. Use `sent_location`, `write_location`,
`flush_location`, `replay_location` and `pg_xlog_location_diff()`; the `write_lag`,
`flush_lag` and `replay_lag` interval columns do not exist on 6.x.

## Lifecycle: `gpstart`, `gpstop`, and reload-versus-restart

```sh
gpstart -a                 # start everything, no prompt
gpstop  -a -M fast         # stop, rolling back in-flight transactions
gpstop  -a -M fast -r      # restart
gpstop  -u                 # reload postgresql.conf and pg_hba.conf, no downtime
```

`gpstop -M` takes `smart | fast | immediate`, **default `smart`**
(`gpMgmt/bin/gpstop`). `smart` waits for every user connection to disconnect, so on a
busy cluster `gpstop -a` can appear to hang forever — that is the default doing its job,
not a bug. `-f`/`-i`/`-s` are the deprecated spellings; `-f` or `-i` together with
`-M fast|immediate` is rejected: `Can not mix --mode options with older deprecated '-f,-i,-s'`.

`gpstart` flags worth knowing (`gpMgmt/bin/gpstart`): `-R` restricted mode (superusers
only), `-m`/`-c` coordinator-only maintenance mode, `-y` skip the standby, `-t` startup
timeout. Coordinator-only mode warns it `may lead to a split-brain condition and possible
unrecoverable data loss.` and that `Maintenance mode should only be used with direction
from Greengage Support.` — heed it: starting the coordinator alone while a standby exists
is how you get a split brain.

Startup failures, verbatim from `gpMgmt/bin/gpstart`:

| String | Cause |
|---|---|
| `Coordinator instance process running` | Already up, or a stale postmaster |
| `Port %s is already in use` | Something else holds `PGPORT` |
| `Catalog Versions are incompatible` | Binaries and data directory are from different builds — see [greengage-build](../greengage-build/SKILL.md) |
| `Standby activated, this node no more can act as coordinator.` | The standby was promoted; this host is now the old coordinator |
| `Do not have enough valid segments to start the array.` | At least one `content` has neither a working primary nor a working mirror |
| `There are %d segment(s) marked down in the database` | Cluster started degraded; run `gprecoverseg` |
| `Found a System Expansion Setup in progress. Please run 'gpexpand --rollback'` | A `gpexpand.status` file is in the coordinator data directory |

### `gpconfig` changes the file; something else has to make it take effect

```sh
gpconfig -s gp_fts_probe_interval          # current value, per segment
gpconfig -c gp_fts_probe_interval -v 30    # write to every postgresql.conf
gpconfig -r gp_fts_probe_interval          # remove the setting
gpstop -u                                  # reload  (PGC_SIGHUP and looser)
gpstop -a -M fast -r                       # restart (PGC_POSTMASTER)
```

The rule is the GUC's context, taken from `src/backend/utils/misc/guc_gp.c`:

| Context | Example | Applies after |
|---|---|---|
| `PGC_POSTMASTER` | `gp_vmem_protect_limit`, `gp_workfile_limit_per_segment` | `gpstop -a -M fast -r` — **only** a full restart |
| `PGC_SIGHUP` | `gp_fts_probe_interval`, `gp_fts_probe_timeout`, `gp_fts_probe_retries` | `gpstop -u` |
| `PGC_USERSET` / `PGC_SUSET` | `gp_workfile_limit_per_query`, `optimizer` | `gpstop -u`, or `SET` in session |

Traps, all read from `gpMgmt/bin/gpconfig`:

- **`gpconfig` requires the cluster to be up.** `Failed to connect to database, exiting
  without action. This script can only be run when the database is up.` There is no
  offline mode; edit `postgresql.conf` by hand if the cluster will not start.
- `port` and `listen_addresses` are in `PROHIBITED_GUCS`: `The parameter 'port' is not
  modifiable with this tool`. Do not reach for `--skipvalidation`, which bypasses it.
- `-c` and `-r` refuse to run mid-expansion: `ERROR: Usage of gpconfig is not supported
  while the cluster is in a reconfiguration state, exit gpconfig`.
- `-s` reads the **running** value. Use `--file` to read what is on disk and
  `--file-compare` to see both — that is how you catch a change written but never applied.
- Concurrent `gpconfig` runs for the same GUC are not serialized (see the header comment
  in `gpMgmt/bin/gpconfig`). One run at a time.

Cross-check for drift the catalog will not show you:

```sql
SELECT psdname, psdvalue, psdcount
FROM   gp_toolkit.gp_param_settings_seg_value_diffs
ORDER  BY psdname;
```

Any row means at least one segment disagrees with the rest. On 7.x `gp_toolkit` is an
extension (`CREATE EXTENSION gp_toolkit`, `gpcontrib/gp_toolkit`); on 6.x it is loaded
into every database by `initdb`.

## Recovery: use the ladder, in order

The full decision tree, signatures and ordering constraints live in
[reference/recovery.md](reference/recovery.md). The one rule that belongs here:

**`gprecoverseg -r` before every pair is `mode = 's'` silently does less than you asked.**
The rebalance skips any pair that is not up, reachable and synchronized, logging
`Not rebalancing primary segment dbid %d with its mirror dbid %d because one is either
down, unreachable, or not synchronized` (`gppylib/operations/rebalanceSegments.py`) — then
still prints `The rebalance operation has completed successfully.` Recover first, wait for
`mode = 's'` on every row, then rebalance.

## Growing the cluster

`gpexpand` adds segments; it runs in two phases and takes a **catalog lock** in phase 1
(`select gp_expand_lock_catalog()` plus a `CHECKPOINT`, `gpMgmt/bin/gpexpand:1297-1298`).
While that lock is held, other utilities refuse to start rather than corrupt the catalog:

```
ERROR: Usage of gpcheckcat is not supported while the cluster is in a
reconfiguration state, exit gpcheckcat
```

`gpcheckcat` and `gpconfig` both call `conflict_with_gpexpand()`
(`gpMgmt/bin/gppylib/commands/gp.py:1377`). Do not work around it. Monitor with
`gpstate -x`, the `gpexpand.expansion_progress` view and the `gpexpand.status_detail`
table; remove the expansion schema with `gpexpand -c` when redistribution finishes
([Expand a cluster](https://greengagedb.org/en/docs-gg/current/expand_cluster.html)).

`ggrebalance` is a **Greengage-original utility, 7.x only, added in 7.5.0**. It changes
cluster topology — redistributing segments across hosts, adding or removing hosts — where
`gpexpand` only adds. Absent on 6.x and on 7.x before 7.5.0, so check `which ggrebalance`
first. Its [docs page](https://greengagedb.org/en/docs-gg/7/reference/utils/ggrebalance.html)
is one of the few that exists only in the `/7/` documentation tree.

## Hygiene for long-running work

A cluster used for regression runs, load testing or spill-heavy analytics fills its disks
before it does anything else interesting.

```sql
-- Free space per segment, in KB (an external web table; each segment runs `df -Pk`)
SELECT dfsegment, dfhostname, dfdevice, dfspace
FROM   gp_toolkit.gp_disk_free
ORDER  BY dfspace;

-- Spill files right now, per segment
SELECT segid, size, numfiles
FROM   gp_toolkit.gp_workfile_usage_per_segment
ORDER  BY size DESC;

-- Which query is doing it
SELECT datname, pid, sess_id, usename, segid, size, numfiles, query
FROM   gp_toolkit.gp_workfile_usage_per_query
ORDER  BY size DESC
LIMIT  10;
```

| Symptom | Cause | Fix |
|---|---|---|
| `gp_disk_free` shrinking during a run, `gp_workfile_usage_per_segment` large | Spill files from hash joins/sorts that exceed work memory | Cap it: `gp_workfile_limit_per_segment` (KB, default `0` = unlimited, **`PGC_POSTMASTER`**), `gp_workfile_limit_per_query` (KB, `PGC_USERSET`), `gp_workfile_limit_files_per_query` (default `100000`) |
| `core.*` files piling up in segment data directories | A backend crashed. The postmaster `chdir`s to `DataDir` at startup (`ChangeToDataDir()`, `src/backend/postmaster/postmaster.c:1079`), so with a relative `kernel.core_pattern` every core lands in a data directory — one per crashed segment, on every host | Delete them after capturing what you need — see [greengage-debug](../greengage-debug/SKILL.md). Nothing cleans them up for you |
| `Canceling query because of high VMEM usage. Used: NMB, available NMB, red zone: NMB` | The session crossed the red zone — `runaway_detector_activation_percent` (default `90`) of `gp_vmem_protect_limit` (`src/backend/utils/mmgr/runaway_cleaner.c:189`) | Per-segment memory ceiling, not per-host. On a demo cluster with many segments on one host it fires early. `gp_vmem_protect_limit` is `PGC_POSTMASTER` — raising it needs a restart |
| A segment host OOM-kills postmasters, `status` flips to `d` | Segments-per-host times `gp_vmem_protect_limit` exceeds real RAM | Reduce `NUM_PRIMARY_MIRROR_PAIRS` on a demo cluster, or lower the limit |
| Demo cluster fails to initialize in a container | Too few SysV semaphores | `--sysctl "kernel.sem=500 1024000 200 4096"` — see [reference/provisioning.md](reference/provisioning.md) |

## What NOT to do

- **Do not write anything in utility mode.** `PGOPTIONS='-c gp_session_role=utility'` (the
  spelling that works on both lines) bypasses the dispatcher; an INSERT or DDL there lands
  on one instance and desynchronizes the cluster.
  Read-only inspection only. The server tells you as much when you connect to a primary
  without it: `connections to primary segments are not allowed`, hint
  `To force a connection anyway (dangerous!), use utility mode.`
  (`src/backend/utils/init/postinit.c`).
- **Do not conclude a segment is broken from `role <> preferred_role`.** That is a
  completed failover, not a failure. See the signature table above.
- **Do not conclude the coordinator is degraded from `mode = 'n'`.** Filter
  `content > -1`.
- **Do not run `gprecoverseg -r` while anything is `mode = 'n'`.** It skips the unready
  pairs, warns rather than failing, and still reports success.
- **Do not `gpstart -m` on a cluster that has a standby** unless you have confirmed the
  standby is stopped. Split brain.
- **Do not rerun `make create-demo-cluster` to "refresh" a cluster you still need.** It
  deletes `$DATADIRS` first.
- **Do not trust a `gpstate` run whose environment you did not just source.** A stale
  `COORDINATOR_DATA_DIRECTORY` reports on a cluster that no longer exists.
- Ignore this noise: a `gpinitsystem` exit code of 1, which means warnings and which
  `demo_cluster.sh` deliberately maps to exit 0 (`gpinitsystem will return warnings as
  exit code 1`); the `<deprecated>` tags on `gpstop -f`/`-i`/`-s`, which still work; and
  `mode = 'n'` on `content = -1`.
