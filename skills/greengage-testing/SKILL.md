# Running Greengage's tests

Greengage has two regression harnesses (`src/test/regress` and `src/test/isolation2`), a
Python BDD suite (`gpMgmt` behave), a C++ unit suite (GPORCA ctest) and a mock unit suite
(`unittest-check`). Everything except `unittest-check` and ORCA ctest runs **against an
already-running cluster**. Full inventory: [reference/suites.md](reference/suites.md).

## Environment first — the suites fail in confusing ways without it

```sh
source /usr/local/gpdb/greengage_path.sh   # 7.x README prefix; CI container: /usr/local/greengage-db-devel
source gpAux/gpdemo/gpdemo-env.sh          # generated by demo_cluster.sh, git-ignored
export LANG=en_US.UTF-8                    # README: "Tests require a UTF-8 compatible locale"
```

Sourcing `greengage_path.sh` alone is **not** enough. Several regress and isolation2 tests
shell out to `gpconfig`/`gpstop`, which abort with `Environment Variable
COORDINATOR_DATA_DIRECTORY not set!` (`gpMgmt/bin/gppylib/commands/gp.py:1230`; 6.x says
`MASTER_DATA_DIRECTORY`, at line 1207) or `USER environment variable must be set.`
(`gpMgmt/bin/gpconfig:95`). Inside a container, `docker exec` must pass `-e USER=gpadmin`.
Set the locale **before** creating the cluster: the databases inherit `initdb`'s encoding.

## `make check` and `make installcheck` are not the PostgreSQL targets

`src/test/regress/Makefile` is a stub that only prints *"You must use GNU make"*. The real
rules are in `src/test/regress/GNUmakefile`, and the upstream `installcheck` rule
(`--schedule=serial_schedule`) is **commented out** there and replaced by an alias:

```make
#installcheck: ... --schedule=$(srcdir)/serial_schedule ...   # GNUmakefile:223-224
installcheck: installcheck-good                               # GNUmakefile:225
```

| Target | What it actually does |
|---|---|
| `make -C src/test/regress check` | upstream temp-instance `pg_regress --temp-instance` — a single-node PostgreSQL. **Cannot work for Greengage.** |
| `make -C src/test/regress installcheck` | alias for `installcheck-good` |
| `make -C src/test/regress installcheck-good` | `--schedule=parallel_schedule --schedule=greengage_schedule` into one `regression` db |
| `make installcheck-world` (top level) | the everything target CI runs; adds `gpcheckcat -A` and — 7.x only — `vacuumdb --all --analyze-only --jobs=5` |
| `make check` (top level, 7.x) | installs if needed, creates a demo cluster if `pg_isready` fails, then runs `installcheck` |

The README still says *"The PostgreSQL __check__ target does not work"* — true for
`src/test/regress check`, and true for 6.x, whose top-level `check` just recurses there. 7.x
gave the top-level `check` its own recipe (`GNUmakefile.in:163-175`) that bootstraps a
cluster; prefer the explicit sequence anyway, since that wrapper will `make install` into
`$(prefix)` whenever `$(prefix)/greengage_path.sh` is missing. **New tests go in
`greengage_schedule`, never in `parallel_schedule` or `serial_schedule`** — README: *"We try
to keep the upstream tests identical to the upstream versions, to make merging with newer
PostgreSQL releases easier."*

## The two schedules share one database, and that is deliberate

`installcheck-good` passes two `--schedule` files with one default `--dbname=regression`
(`pg_regress_main.c:173`). Exactly three test names appear in both 7.x schedules —
`test_setup`, `disable_autovacuum`, `enable_autovacuum` — and all three are re-runnable
(`sql/test_setup.sql:8` drops and recreates schema `test_util`); on 6.x the two schedules
share no name at all. A fourth duplicate silently double-executes; check before you add one:

```sh
comm -12 <(grep '^test:' parallel_schedule | sed 's/^test: *//' | tr ' ' '\n' | sort -u) \
         <(grep '^test:' greengage_schedule | sed 's/^test: *//' | tr ' ' '\n' | sort -u)
```

`installcheck-good` passes **no** `--max-connections`. Only `installcheck-parallel`,
`check`, `check-tests` and `bigcheck` honour `MAX_CONNECTIONS=N`; cap the full run with
`EXTRA_REGRESS_OPTS='--max-connections=8'` instead. 7.x additionally caps concurrent tests
at 20 via `REGRESS_OPTS = --dlpath=. --max-concurrent-tests=20 --init-file=…`; 6.x's
`REGRESS_OPTS` has no such cap.

## A single-test run is not authoritative, and the two ways to do it fail differently

```sh
# (a) make target: DROPS and RECREATES the regression database first
make -C src/test/regress installcheck-tests TESTS="qp_misc gp_dqa"

# (b) direct, against the database a schedule run left behind
make -C src/test/regress tablespace-setup
cd src/test/regress
PGOPTIONS="-c optimizer=off" \
  "$(pg_config --pkglibdir)/pgxs/src/test/regress/pg_regress" \
  --inputdir=. --bindir="$GPHOME/bin" --dlpath=. --use-existing --dbname=regression \
  --init-file=init_file qp_misc
```

- **(a) destroys your `regression` database.** `pg_regress_installcheck`
  (`src/Makefile.global.in:758`) carries no `--use-existing`, so `pg_regress` calls
  `drop_database_if_exists()` then `create_database()` (`pg_regress.c:3330,3348`). On a fresh
  database any test depending on the setup chain fails at once: `tenk1` and `onek` come from
  `create_table`, `tenk1`'s rows from `copy` (`input/copy.source:18`), and `create_function_1`
  → `create_type` → `create_table` → `create_function_2` are four serial groups at the head
  of `parallel_schedule` (lines 37-40). Reproduce the prefix:

  ```sh
  awk '/^test:/{sub(/^test: */,"");printf "%s ",$0} /<yourtest>/{exit}' parallel_schedule
  ```

- **(b) inherits every table the previous run left behind.** Tests create scratch objects
  and rarely drop them. A pass here proves nothing; a failure here may be pollution.
  `--use-existing` also skips `create_database()`, and `--load-extension` is applied
  *inside* `create_database()` — so a fault-injection test run this way fails with
  `function gp_inject_fault(...) does not exist` unless the extension is already there.

**The authoritative result is a fresh full-schedule run.** Use single-test runs to iterate,
then confirm with `make -C src/test/regress installcheck-good`.

## `optimizer=on` and `optimizer=off` do not share one answer file

`optimizer` defaults to `on` in an ORCA build (`src/backend/utils/misc/guc_gp.c:1815`, under
`#ifdef USE_ORCA`; 6.x is identical at line 2109), so a bare run exercises GPORCA. `pg_regress`
probes the live setting with `psql -X -t -c "show optimizer;" -d postgres` and prints one of:

```
Optimizer enabled. Using optimizer answer files whenever possible
Optimizer disabled. Using planner answer files
```

Selection ladder (`pg_regress.c:1112-1141`), first hit wins:

| Order | File | Condition |
|---|---|---|
| 1 | whatever `resultmap` names | testname/platform entry matches — 7.x's `resultmap` holds only three cygwin/mingw/hpux `float4` lines, so this never fires on Linux |
| 2 | `expected/<t>_optimizer_resgroup.out` | `optimizer=on` **and** resgroup — no such file exists on either line |
| 3 | `expected/<t>_optimizer.out` | `optimizer=on` (153 such files in 7.x, 106 in 6.x) |
| 4 | `expected/<t>_resgroup.out` | `show gp_resource_manager` is **exactly** `group` — `group-v2` does not match (`pg_regress.c:3363`); 5 such files |
| 5 | `expected/<t>.out` | fallback |
| — | `expected/<t>_0.out` … `<t>_9.out` | numbered alternates; a *complete* match on any of them passes |

**Consequence for regeneration:** if a test has no `_optimizer.out`, the base `<t>.out` is
shared and must satisfy both optimizers — never regenerate it from an `optimizer=on`-only
run. Do not guess which file to edit: the header `regression.diffs` writes before each hunk
names it exactly (`pg_regress.c:2010`):

```
diff -I HINT: -I CONTEXT: -I GP_IGNORE: -U3 expected/qp_misc_optimizer.out results/qp_misc.out
```

Both optimizer paths must be green — run each as its own pass with `PGOPTIONS='-c
optimizer=on'` / `-c optimizer=off` (`ci/readme.md`). Details of regenerating:
[greengage-answer-files](../greengage-answer-files/SKILL.md).

## gpdiff normalises at diff time; the expected files store raw output

`pg_regress` never calls `diff` directly — it calls `gpdiff.pl`, which pipes both sides
through `atmsort.pm` first, with `-I HINT: -I CONTEXT: -I GP_IGNORE:` (`pg_regress.c:76`).
What that means in practice:

- **Unordered `SELECT` output is sorted before comparison.** A result-set order difference
  is not a diff unless the query has an `ORDER BY` (then the order is compared, so a
  partial `ORDER BY` needs `-- order 1,2` or `-- order none`).
- **`EXPLAIN` / `EXPLAIN ANALYZE` output is reduced** to a nested `id`/`parent`/`short`
  structure by `explain.pm` with `PRUNE => 'heavily'`, and its `(N rows)` line is always
  prefixed `GP_IGNORE:` (`atmsort.pm:1148-1157`). Costs, timings, per-segment row counts
  and slice statistics therefore **cannot** cause a diff.
- **`EXPLAIN (COSTS OFF)` is the exception**: `atmsort.pm:1201` tags it `costs_off` and skips
  the reformatting, so it is compared verbatim. Plan-shape churn shows up here and nowhere else.
- `init_file` masks the rest: `m/^ Settings:.*/` (line 24), the four `m/^ Optimizer: …/`
  variants (lines 20-23 — each optimizer spelling is its own pattern), the `'DISTRIBUTED
  BY' clause` NOTICE/HINT family, anonymous partition names, `pg_temp_NNN` schemas,
  `(dbsize.c:NNN)`-style source line numbers, and it normalises the `QUERY PLAN` header and
  its dashed separator to a fixed width — explicitly *"because we invoke same test with
  different sets of PGOPTIONS"*.

Write masks into the test's own `-- start_matchsubs` block, not into `init_file`, unless the
pattern is genuinely global.

## isolation2 is a different harness with a different failure mode

```sh
make -C src/test/isolation2 install          # installcheck runs the INSTALLED binary
make -C src/test/isolation2 installcheck     # 272 test lines, db isolation2test
```

`pg_isolation2_regress_installcheck` invokes `$(pgxsdir)/src/test/isolation2/pg_isolation2_regress`
(`src/Makefile.global.in:783`) — the copy under `$(pg_config --pkglibdir)/pgxs`, not the one
in your build tree. Edit the harness or `sql_isolation_testcase.py`, forget `make install`,
and you test the old one. `installcheck` also chains `installcheck-resource-queue`,
`-parallel-retrieve-cursor`, `-ic-tcp` and `-ic-proxy` before its own schedule.

Facts that save time:

- **The spec syntax is documented in `src/test/isolation2/sql_isolation_testcase.py`**
  (docstring of `class SQLIsolationTestCase`). Session prefixes: `1:` plain, `1&` expect
  blocking, `1>` background, `1<` join, `1q` quit, `<content-id>U` utility mode, `R`
  retrieve, `S` standby, `M` mirror, `*U` every primary plus the coordinator. `!` runs a
  shell command; `!\retcode` wraps its output in `start_ignore` and prints the exit code.
  `S` and `M` are absent from that docstring — they exist only in the code, at lines 663-670.
- **`sql/setup.sql` runs automatically before every spec**, including single-spec runs
  (`isolation2_main.c:149` adds `setup` to `setup_tests`). It does **not** create
  `gp_inject_fault`; that comes from `FAULTINJECTOR_OPTS`' `--load-extension`, which is why
  a make-driven run needs no manual `CREATE EXTENSION`.
- The harness splits statements on a trailing `;`, **with no understanding of
  dollar-quoting**. Multi-line function bodies must end each line with a `/* in func */`
  comment — see the comment at the head of `sql/setup.sql`.
- Killing a fault-injection spec mid-flight leaves the fault armed, workers suspended and
  transactions in doubt. Kill the `python3 sql_isolation_testcase.py` process, reset the
  fault, and if the cluster is still wedged recreate it —
  [greengage-cluster-ops](../greengage-cluster-ops/SKILL.md). `pkill -f pg_isolation2_regress`
  from inside a `docker exec` shell matches its own command line and kills the shell.

## Without debug extensions your fault tests are skipped, not run — and they exit 0

`src/Makefile.global.in:528-544` switches on `enable_debug_extensions`:

| Build | `FAULTINJECTOR_OPTS` | Effect |
|---|---|---|
| debug extensions on | `--load-extension=gp_inject_fault` | fault tests run |
| debug extensions off | `--exclude-file=tests_using_faultinjector.txt` | every test matching `(select\|perform)\s.*gp_inject_fault` is **excluded and counted as absent** |

`gpcontrib/Makefile` only builds `gp_inject_fault`, `gp_debug_numsegments` and
`gp_replica_check` when the flag is set, so this is self-consistent — but the run still
exits 0 with a smaller test count.

**The default differs by line** (`configure.in`, `PGAC_ARG_BOOL(enable, debug-extensions, …)`):
7.x defaults to **yes** (line 225), 6.x defaults to **no** (line 212). On 6.x you must
pass `--enable-debug-extensions` explicitly or you will silently test nothing that injects
a fault. Packaged builds turn it off on both lines — the `package` job in
`.github/workflows/greengage-ci.yml:143` is commented *"Rebuild prod-ready version without
debug extensions"*.

`pg_regress` prints `faultinjector enabled` or `faultinjector not enabled` before the tests
start (`pg_regress.c:3337-3339`, `#ifdef FAULT_INJECTOR`, defined by the same configure
flag); check that line before believing a green fault-injection run.

## `scan_flaky_fault_injectors.sh` fails the run before a single test executes

On a debug-extensions build, every regress, isolation and isolation2 `installcheck` is
prefixed by `src/test/regress/scan_flaky_fault_injectors.sh &&` (the `faultinjector_prep`
define, `src/Makefile.global.in:528-532`). It intersects the tests that call
`gp_inject_fault` with those sitting in a multi-entry `test:` group, and exits 1 with:

```
ERROR: above tests are flaky as they inject faults and are put in parallel testing groups.
HINT: move each of them to a separate testing group.
```

This is not a test failure — it is a schedule lint. Fix it by giving the test its own
`test:` line. It is the one flaky class the tree defines mechanically; treat everything else
as a real failure until two or three reruns prove otherwise, then take the **intersection**
of the failing sets as the deterministic part.

## `installcheck-resgroup` reconfigures and restarts your cluster

The first spec of each resource-group schedule (`resgroup/resgroup_auxiliary_tools_v1`, or
`…_v2`) runs, via `!` shell escapes:

```sql
! gpconfig -c gp_resource_manager -v group;      -- v1; group-v2 in the v2 schedule
! gpconfig -c max_connections -v 250 -m 25;
! gpconfig -c runaway_detector_activation_percent -v 100;
! gpstop -rai;
```

Your demo cluster is left in resource-group mode afterwards. Run resgroup suites **last**,
or reset with `gpconfig -c gp_resource_manager -v queue && gpstop -rai`.

| Target | GUC it sets | cgroup layout it checks | Branch |
|---|---|---|---|
| `installcheck-resgroup` | `gp_resource_manager=group` | v1: `/sys/fs/cgroup/{cpu,cpuacct,cpuset}/gpdb` | both |
| `installcheck-resgroup-v2` | `gp_resource_manager=group-v2` **plus** `gp_resource_group_cgroup_parent=gpdb` | v2: `/sys/fs/cgroup/gpdb/*` | **7.x only** |

Both need `plpython3u` and a writable cgroup tree — `ci/scripts/run_resgroup_test.bash` runs
the container `--privileged` and `chmod -R 777`s the hierarchy first. 6.x has a single
`isolation2_resgroup_schedule` and no v2 target; semantics live in
[greengage-workload-management](../greengage-workload-management/SKILL.md).

## The JIT matrix (7.x only) proves nothing on a non-LLVM build

JIT tests are the ordinary regress tests with JIT forced on — no separate schedule, no
separate answer files. `MAKE_TEST_COMMAND` values from `ci/readme.md` — `ic_gpdb.bash:34`
runs them as `PG_TEST_EXTRA="kerberos ssl" make -s $MAKE_TEST_COMMAND`:

```
-k PGOPTIONS='-c optimizer=on  -c jit=on -c jit_above_cost=0 -c optimizer_jit_above_cost=0 -c gp_explain_jit=off' installcheck
-k PGOPTIONS='-c optimizer=off -c jit=on -c jit_above_cost=0 -c gp_explain_jit=off' installcheck
```

`optimizer_jit_above_cost` is ORCA-only and is dropped from the planner variant.
`gp_explain_jit=off` suppresses the `JIT:` block in `EXPLAIN ANALYZE`
(`src/backend/commands/explain.c:1138`), which is what lets JIT runs reuse the non-JIT
expected files.

**`--with-llvm` defaults to `no`** (`configure.in:426`). If `llvmjit.so` is absent,
`provider_init()` checks `file_exists()` and returns false with only a `DEBUG1` message
(`src/backend/jit/jit.c:93-95`) — `jit=on` is accepted and nothing is compiled. Confirm with
`SELECT pg_jit_available();` before attributing anything to JIT. 6.x has no JIT at all: no
`src/backend/jit`, no `--with-llvm` in `configure.in`, no `jit-tests` CI job.

## behave needs a 4-host cluster for some scenarios and a tag filter for the rest

```sh
# full/parallel, docker-compose, 3 features at a time
IMAGE=greengage7_u22:${BRANCH_NAME} bash ci/scripts/run_behave_tests.bash gpstart gpstop

# one feature against the local demo cluster (must be run from gpMgmt, with GPHOME set)
cd gpMgmt && make -f Makefile.behave behave tags=gpstart
```

- `run_behave_tests.bash` hardcodes `clusters="~concourse_cluster"` and passes `--tags
  $feature --tags=~concourse_cluster`. A scenario tagged **both** `@concourse_cluster` and
  `@demo_cluster` is still excluded — the script's own comment is *"TODO concourse_cluster
  tests are not stable"*. Use the same filter locally or you will collect failures from
  scenarios that need the 4-host `cdw`+`sdw1..3` compose cluster.
- With no arguments it runs all 23 features **except** `cross_subnet`, `gpssh`, `gpexpand`.
- `Makefile.behave` refuses to run without `tags=` or `flags=`, and needs `behave` on `PATH`
  (`pip install -r gpMgmt/requirements-dev.txt`). It builds `PYTHONPATH` itself from
  `$(GPHOME)/bin/lib` and `$(CURDIR)/test` (6.x also adds `test/behave/mgmt_utils/steps`), so
  run it from `gpMgmt` with `GPHOME` exported. Scenarios start, stop and reconfigure real
  clusters — never run behave beside a regress run you care about.

## Two suites need no cluster — run them before you start one

```sh
make -s unittest-check                                   # cmockery mocks, backend + src/bin
cd src/backend/gporca && cmake -GNinja -H. -Bbuild && ninja -C build
cd build && ctest -j8 --output-on-failure                # GPORCA C++ unit tests
```

`unittest-check` recurses with `CFLAGS=-DUNITTEST` into `src/backend` (every `**/test/`
directory's mock binaries) and `src/bin` (only `pg_dump/test`, `src/bin/Makefile:16`). It is
serial and aborts on the first failing binary, so a red result may hide more.

ORCA ctest details are in `src/backend/gporca/README.md` — its "go into the `gporca`
directory" means `src/backend/gporca`. `./server/gporca_test -U <TestName>` runs one suite,
`-d ../data/dxl/minidump/<X>.mdp` one minidump, and `src/backend/gporca/scripts/fix_mdps.py
--logFile <ctest output>` rewrites failing minidumps (`--dryRun` first). Some assertions
exist only in `CMAKE_BUILD_TYPE=Debug` builds, so a Release ctest is the weaker check.

## A green test line is not a pass

| Symptom | Cause | What to check |
|---|---|---|
| Suite "passed" but the count is low | fault tests excluded on a non-debug-extensions build | the `faultinjector enabled` / `faultinjector not enabled` header |
| `TAP tests not enabled` | built without `--enable-tap-tests` | `src/Makefile.global.in:524` — the target is a no-op echo |
| `icudp tests can not run in production builds, skipped` | `BUILD_TYPE=prod` | rebuild non-prod |
| `installcheck-ic-tcp` / `-ic-proxy` finish instantly | the recipe is inside `ifeq ($(findstring gp_interconnect_type=…,$(PGOPTIONS))…)` | pass the matching `PGOPTIONS` |
| Every later `contrib` test fails at `DROP DATABASE` | a hung session still holds `contrib_regression` | kill leftover backends between extensions |
| `gpcheckcat -A` fails in `installcheck-world` | an aborted `src/test/isolation` run left `isolation_regression` behind (its `dropdb` is a separate make line that only runs on success) | `dropdb isolation_regression` |
| Diff hunks you cannot explain | you regenerated the wrong file | the `diff … <expected> <results>` header line in `regression.diffs` |

The definitive pass signal is the tally line plus an **absent** `regression.diffs`:
`pg_regress` truncates it at start and `unlink`s both it and `regression.out` on a clean run
(`pg_regress.c:3446-3459`), which `.gitignore` documents as *"regreesion.\* are only left
behind on a failure"*. The four literal tally forms (`pg_regress.c:3414-3435`):

```
 All 197 tests passed.
 3 of 197 tests failed.
 195 of 197 tests passed, 2 failed test(s) ignored.
 5 of 197 tests failed, 2 of these failures ignored.
```

## `.source` templates, not the generated files

`input/*.source` → `sql/*.sql` and `output/*.source` → `expected/*.out` are generated at
run start by `convert_sourcefiles()` (`pg_regress.c:963`), substituting `@abs_srcdir@`,
`@abs_builddir@`, `@testtablespace@`, `@libdir@`, `@DLSUFFIX@`, `@bindir@`, `@hostname@`,
`@curusername@`, `@cgroup_mnt_point@` (`pg_regress.c:588-596`). The generated files are
**not tracked** — edit the `.source`. A subdirectory of `input/`/`output/` holding a
`GENERATE_ROW_AND_COLUMN_FILES` marker (regress: `uao_ddl/`, `uao_dml/`; isolation2: `uao/`)
generates `_row` and `_column` variants of every `.source` in it, substituting `@amname@`
and `@aoseg@`. Audit for misplaced templates:

```sh
git ls-files '*.source' | grep -vE '/(input|output|yml_in)/'   # only src/tutorial should match
```

## What not to do

- Do not run `make -C src/test/regress check`, or edit `src/test/regress/Makefile`.
- Do not add tests to `parallel_schedule` or `serial_schedule`.
- Do not treat a single-test result as evidence — neither the fresh-db form nor the
  `--use-existing` form is authoritative.
- Do not regenerate a base `<t>.out` from an `optimizer=on` run when no `_optimizer.out`
  exists, and never regenerate a diff whose result side is an `ERROR`.
- Do not run the resgroup suites, behave or `make -C src/bin/pg_upgrade check` beside a run
  you are measuring — all three stop, restart or replace clusters.
- Do not chase EXPLAIN cost, timing or per-segment row-count differences: atmsort already
  removed them, so if you see one the query is `EXPLAIN (COSTS OFF)` and the plan changed.
- Do not conclude "JIT bug" before `SELECT pg_jit_available();` returns `t` (7.x only —
  6.x has no `src/backend/jit` at all).
